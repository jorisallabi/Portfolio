09 / Projet phare · Système local multi-agents

ATLAS : assistant personnel avec n8n et IA

ATLAS est un assistant personnel que j’utilise depuis Telegram. Il tourne en local avec n8n et répartit les demandes entre plusieurs modules. Il gère les tâches, l’agenda, les projets et la recherche d’emploi au Bénin. La base conserve les données. Le code vérifie les demandes avant toute action.

01 / Architecture & flux

Telegram, quatre workflows et une base de données.

Telegram déclenche le routeur ATLAS via un webhook exposé par ngrok. Le webhook répond immédiatement à Telegram, puis le planificateur intercepte les demandes de projets et les listes de tâches. Les autres messages sont routés vers JARVIS ou JERICHO selon leur nature.

Repli tolérant aux pannes : si Ollama ne répond pas, le routeur envoie le message vers JERICHO au lieu de le perdre. Les commandes JARVIS explicites et les callbacks de boutons suivent des chemins déterministes, sans dépendre du LLM.

Rôle exact du LLM

Le modèle local qwen3.5:9b est appelé avec une température de 0,1 et une sortie d'appel d'outils. Son périmètre est volontairement réduit : traduire une phrase libre en une commande structurée et proposer un plan de projet en JSON contraint. Il n'effectue aucune écriture directement. Une fonction de planification convertit l'appel d'outil en commande ; les modules métier et la base contrôlent ensuite les données et l'exécution.

Quatre workflows publiés

01 / ROUTAGE

ATLAS · Routeur Telegram

Point d'entrée, vérifications de sécurité, routage des commandes et planification assistée.

02 / PRODUCTIVITÉ

JARVIS · Tâches & agenda

Gestion déterministe des tâches, événements, projets et rappels, avec synchronisation Google Agenda.

03 / COLLECTE

JERICHO · Emploi

Scraping multi-sources, notation, suivi des offres et validation humaine, sans LLM.

04 / SYNCHRONISATION

TRELLO · Vue globale

Synchronisation bidirectionnelle entre la base et les cartes Trello, avec détection des changements.

02 / Module JARVIS

Gérer les tâches et les projets.

JARVIS gère les tâches, les événements et les projets. L'analyse des commandes courantes repose sur des expressions régulières, des règles métier et des requêtes SQL : aucune génération libre par LLM n'intervient dans l'exécution quotidienne.

Gestion déterministe des tâches et de l'agenda

Dates, heures, durées, priorités et lieux sont extraits par règles et expressions régulières. JARVIS gère les tâches en retard, les échéances, les événements, les conflits de calendrier et les rappels à envoi unique. Une modification d'heure réarme le rappel.

Planification de projets complexes

ATLAS pose d'abord des questions de clarification, puis le LLM propose un plan JSON : jalons, tâches, durées et dépendances. Le code contrôle les références, les limites, les dépendances et les cycles. Le calendrier est ensuite calculé par le code selon la capacité hebdomadaire ; le LLM ne choisit aucune date. Un aperçu est présenté pour validation avant création.

Transactions, validation et idempotence

Les lots sont intégralement validés avant la moindre écriture, puis insérés en une seule opération. La décomposition d'un projet passe par la fonction SQL atlas_create_project_tree : projet, jalons, tâches et dépendances sont créés ensemble ou pas du tout. Un request_id unique empêche une demande rejouée de créer des doublons.

03 / Module JERICHO

Un pipeline d'offres d'emploi sans intelligence artificielle générative.

JERICHO collecte des offres sur cinq sources béninoises : quatre sites HTML et une API JSON. Le traitement est déterministe, depuis l'extraction jusqu'à la notation et à la déduplication.

ExtractionTitre, entreprise, lieu, date limite

Notation pondérée de 0 à 100

Les mots-clés du profil réseaux et systèmes ont des poids différents. FortiGate / Fortinet valent 5 points ; Cisco, CCNA, CCNP, MPLS, BGP, VMware et ESXi valent 4 ; VPN, IPsec, firewall, Zabbix, VoIP et Active Directory valent 3. Un mot-clé présent dans le titre voit son poids doublé ; des intitulés hors profil retirent des points.

Déduplication et critères d'éligibilité

Une clé de déduplication fondée sur le titre normalisé et l'entreprise complète le contrôle d'URL unique. Une offre est proposée à l'approbation si son score atteint le seuil configuré, si elle n'est pas expirée et si elle est localisée au Bénin. Les doublons sont identifiés sans appel au LLM.

Suivi avec validation humaine

Chaque offre candidate est envoyée sur Telegram avec son score, l'entreprise, le lieu, la date limite, les mots-clés détectés et un lien. L'utilisateur peut approuver ou écarter ; les offres approuvées entrent dans le suivi de candidature. Les erreurs de sources sont signalées comme collecte partielle.

04 / Rigueur d'ingénierie

Le code vérifie les actions avant leur exécution.

ATLAS sépare les décisions probabilistes de l'exécution métier. Les modules écrivent en base ; Trello et Google Agenda reflètent cet état et peuvent renvoyer les modifications utilisateur vers la base selon des règles explicites.

Niveaux d'autonomie

Niveau AExécution directe pour les actions autorisées par la règle configurée.
Niveau BExécution avec notification, pour garder une trace visible.
Niveau CValidation requise avant écriture. C'est le niveau par défaut si la règle est absente ou illisible.

Synchronisation bidirectionnelle

BASE ↔ TRELLO

Résolution par instantané

Le système conserve un instantané de la liste et de l'échéance. Un changement de carte est répercuté en base via les outils métier ; sinon, les changements de la base mettent à jour la carte. L'origine des appels évite les boucles.

BASE ↔ GOOGLE AGENDA

Conflits arbitrés

Si la base n'a pas changé depuis le dernier envoi, Google gagne. Si les deux côtés ont changé, la base gagne. Une propriété privée jarvis relie les événements et empêche les doublons.

Contrôles transverses

  • Idempotence : identifiants de requête uniques, anti-doublon Telegram, clés uniques et boutons à usage unique.
  • Atomicité : validation avant écriture, insertion de lots en une fois et transaction SQL pour les arbres de projets.
  • Human-in-the-loop : confirmations des actions destructives, aperçu de projet avant création et approbation des offres.
  • Dégradation gracieuse : repli du routeur, notifications non bloquantes et synchronisation Trello de rattrapage toutes les 30 minutes.
  • Traçabilité : journaux JARVIS / JERICHO, table des exécutions agents et file d'actions.

05 / Données, sécurité & limites

Une architecture documentée à partir des workflows observés.

La base de données est la source de vérité. Les workflows utilisent une API REST de type Supabase / PostgREST sur une instance locale, des fonctions SQL RPC et des tables dédiées aux tâches, événements, projets, offres, journaux et règles d'autonomie.

Précision technique : l'audit a reconstitué le modèle de données à partir des requêtes observées ; le schéma SQL réel n'a pas été inspecté. La formulation « PostgreSQL / Supabase » désigne ici la couche REST/RPC telle qu'elle apparaît dans le code, pas une validation indépendante de l'installation PostgreSQL.

Mesures de sécurité observées

Secret Telegram, liste blanche d'un seul chat, jetons dédiés par webhook, masquage des jetons dans les erreurs, contrôle de doublons et contrats JSON homogènes. Les appels inter-workflows passent par des webhooks locaux protégés.

Limites et points à traiter

L'audit a relevé des secrets présents en clair dans plusieurs nœuds et workflows. Ils doivent être régénérés et déplacés vers les credentials n8n ou des variables d'environnement avant toute exposition publique du dépôt ou de captures de configuration. Un échec sur douze exécutions récentes de JARVIS était visible ; sa cause n'a pas été analysée. L'intervalle exact du cron de rappels JARVIS reste à confirmer dans l'interface.
